# Архитектурные и технологические решения

[К документации](README.md) · [Проект целиком](PROJECT.md)

Это ретроспективный реестр решений, наблюдаемых в коде текущего snapshot.
Обоснования объясняют инженерный смысл реализации; они не выдаются за протокол
неизвестных прошлых обсуждений. Статус «принято» означает, что решение используется
сейчас. Ограничения не следует автоматически превращать в постоянные требования.

## ADR-01. Несколько IR вместо прямого CAP → angr

**Принято.** Бинарная структура, стековая семантика, устранение стека, Soot form
и runtime разделены. Прямой decoder-to-engine сделал бы типы, linking и исполнение
одним трудно проверяемым этапом. Теперь на каждой границе есть модель и проверки,
а JSON/text позволяют локализовать первый неверный результат.

Цена — несколько представлений одних и тех же сущностей и необходимость сохранять
source map. При добавлении инструкции надо обновлять все затронутые уровни.
Пересмотр оправдан только при сохранении проверяемых контрактов и диагностики,
а не ради уменьшения количества файлов.

## ADR-02. Устойчивые CAP keys и явные внешние привязки

**Принято.** CP index не является идентичностью API: порядок записей может меняться.
Keys используют AID/version/class/token/offset; человеческие имена вынесены
в symbols. Это позволяет сравнивать разные промежуточные формы и проверять API
против ожидаемого пакета. Неверная версия или signature должна давать отказ.

Цена — необходимость согласованной symbol configuration. Для interface call
дополнительно нужна полная signature до stack analysis. Будущий EXP importer
может автоматизировать построение таблицы, но не должен угадывать её из nargs.

## ADR-03. Block parameters вместо неявного стека на рёбрах

**Принято.** JVM-like IR выражает входной стек блока параметрами, а исходящие рёбра
передают values. Это делает joins/loops явными и позволяет валидировать dataflow.
Local slots остаются изменяемыми: полный SSA не объявляется.

Цена — Soot должен материализовать parallel copies в edge bridges. Сначала
сохраняются все источники, затем назначения; без этого перестановка на back-edge
неверна. Переход к Shimple потребует отдельного SSA/dataflow дизайна.

## ADR-04. Сохранение fixed-width семантики явными преобразованиями

**Принято.** JCVM short/int slots и storage widths сохраняются в ранних моделях.
В Soot numeric execution используется int32 с явным narrowing/extension.
Python integers без ширины не являются моделью Java overflow.

Цена — больше Units и сложнее source mapping. Зато casts и границы можно проверить
отдельно. Новые div/shifts/unary operations должны получить точную runtime semantics
до изменения whitelist; факт представления операции в IR не достаточен.

## ADR-05. Реальные pysoot objects без Java front-end

**Принято.** Adapter создаёт dataclasses целевой ревизии pysoot напрямую, CLE backend
принимает их из памяти. Уже преобразованный CAP не нуждается в повторном lifting
JAR. Обход Lifter сокращает зависимость от JVM и сохраняет контролируемые CAP origins.

Цена — привязка к структуре pysoot и внутреннему API CLE/angr. Используются version
pins и field contract guard. Diagnostic JSON не становится автоматически форматом
загрузки; для этого нужен отдельный валидируемый importer.

## ADR-06. Метаданные деклараций отдельно от method bodies

**Принято.** Class/Descriptor содержат layout, attrs, tokens, hierarchy и applet AID,
которые нельзя достоверно восстановить из набора использованных выражений.
`ProgramMetadata` и `MethodDetails` сохраняют эти данные рядом с pysoot.

Цена — необходимо проверять согласие двух источников. Missing concrete body,
field owner mismatch и противоречащие flags — ошибки, а не поводы создать заглушку.

## ADR-07. Готовность к исполнению отделена от загрузки

**Принято.** Программа может быть полезна для чтения IR и графа даже при отсутствии
runtime semantics. Loader создаёт проект и отчёт; call-state preparation отдельно
проверяет reachable operations. Это делает границы поддержки наблюдаемыми.

Цена — пользователю нужно различать loaded, resolved, ready и completed. Эти
состояния намеренно отражены в отчётах и документации. Readiness консервативен
и не учитывает все возможные path constraints конкретного запуска.

## ADR-08. Собственный heap с независимым состоянием каждого пути

**Принято.** Java locals/frames остаются в angr, CAP objects/fields/arrays — в
SimStatePlugin. Immutable tuples и замена записей обеспечивают fork isolation.
Reference ownership и actual type проверяются явно; отсутствующие классы и поля
не создаются лениво ради продолжения анализа.

Цена — O(n) выражения при symbolic primitive array access и копирование таблиц
состояния. Длина массива ограничивается analysis budget. Symbolic references,
merge/widen и полноценная GC не реализованы. Оптимизация должна сохранить
наблюдаемую семантику и отсутствие cross-path mutations.

## ADR-09. Возможная неисправность не удаляется удобным constraint

**Принято как текущая политика.** Если нарушение guard выполнимо, состояние
останавливается с code/condition/source. Произвольная concretization и silently
skipped statements запрещены. Это предотвращает ложный вывод «ошибок нет» после
исключения опасных входов.

Цена — нормальные входы смешанного состояния тоже не продолжаются автоматически.
Следующий шаг — явное разделение normal/exceptional states с корректным exception
dispatch, а не ослабление guard. До этого отчёт должен учитывать errored и active.

## ADR-10. Dispatch CAP по токенам

**Принято.** Synthetic method names зависят от offset и не кодируют Java override.
Для virtual call используется CAP method token и сигнатура вдоль actual lineage;
special сохраняет объявленную цель. Полная interface→virtual token map пока
отсутствует, поэтому общий interface dispatch отвергается.

Цена — class metadata является частью исполняемого контракта. Необходимо различать
private/constructor/static и обычные virtual методы; API receiver implementation
проверяется до разрешения interface модели.

## ADR-11. Explicit bounded API profile

**Принято.** Нужные внешние API реализуются Python-моделями, привязанными к точным
CAP keys. Это позволяет исполнить оригинальный апплет и контролировать эффекты,
не объявляя поддержку всей карты. Присланные C-файлы используются как reference,
но отсутствующее native окружение не заменяется фиктивной успешной функцией.

Цена — каждый новый API/вариант поведения требует реализации и тестов. Name1API
специализирован; универсальный registry/profile interface ещё не выделен.
Ключевой материал, transience и object provenance входят в контракт модели.

## ADR-12. Concrete DES при символическом управлении

**Принято как граница текущего этапа.** Управляющие байты APDU могут оставаться
символическими, но DES input/key/IV должны иметь единственное значение. Криптография
считается проверенной библиотечной primitive composition. Свободный symbolic input
не заменяется случайным witness.

Цена — не решаются задачи восстановления произвольного symbolic key через DES.
Для расширения надо выбрать точные bitvector formulas либо явно обоснованную
абстракцию с известной доказательной силой. Иначе выводы анализа станут неверными.

## ADR-13. Транзакции как снимок значений

**Принято для bounded profile.** Snapshot persistent fields/arrays прост и
проверяем; transient data исключаются. Allocation при открытой транзакции
запрещён, чтобы не имитировать неподдержанную семантику object lifetime/rollback.

Цена — копирование состояния и отсутствие commit-buffer capacity/physical NVM/
tear recovery. Обычный return с открытой транзакцией фиксируется как ошибка после
abort; полный JCRE cleanup всех engine fault-путей ещё не реализован.

## ADR-14. Свежие Java-кадры на каждую APDU

**Принято.** Между командами переносится выбранное persistent/API state и constraints,
а стек вызовов создаётся заново. После ISOException предыдущий frame мог завершиться
через Ijk_Exit; его повторное использование теряло исполнение следующей команды.

Цена — явная session abstraction. При нескольких исходах пользователь анализатора
сам выбирает продолжение; merge или произвольный выбор пути не выполняется.

## ADR-15. Один adapter для публичного преобразования CAP в typed input

**Принято в D-07.** `CAPFile.to_model()` делегирует `jcvm_ir.methods_from_cap` и
возвращает `list[MethodInput]`. Ранее отдельная проекция legacy `Method` теряла
metadata; независимое исправление двух преобразований создало бы риск расхождения
signature, static flag, join по offset и координат handlers. Общая реализация
задаёт одинаковые данные и отказы для обоих входов.

Цена — явно изменён контракт старого `to_model()`: тип результата и значение
`offset`, отсутствие legacy `is_extended`. Объекты `MethodInfo` и сырые headers
остаются доступны в компонентной модели. Импорт adapter внутри вызова сохраняет
независимость структурного чтения CAP от IR и runtime; расширенные заголовки
по-прежнему не проходят typed adapter. Миграция описана в руководстве CAP parser.
