# Символьное исполнение Java Card: полный практический гайд на symdemo

Проверено 6 ноября 2026 года на присланных `symdemo.cap`, `symdemo.jca`,
`symdemo.java`, `symdemo.exp`, в среде cap2soot после D-08. Команды ниже рассчитаны
на PowerShell и существующее окружение `.venv-angr10`. Сам контрольный прогон
выполнен в Linux, Python 3.12.14; Windows отдельно не запускался.

Это руководство сопровождается рабочим скриптом `run_symdemo.py`, таблицей
символов и небольшим дополнением среды. Исходный Java и собранный CAP не изменены.
Все четыре файла сборки считаются уже доступными в проекте.

## 1. Что мы хотим узнать

Обычный запуск отвечает на вопрос: «Что произойдёт с этим конкретным запросом?»
Например, мы отправили сумму 1 и увидели успешный ответ.

Символьный запуск отвечает на другой вопрос: «Какие запросы приведут в нужное
место программы?» Вместо выбранных байтов среда создаёт переменные. Когда код
сравнивает значения, к пути добавляются условия. Решатель подбирает значения,
которые удовлетворяют всем условиям выбранного пути.

Наш апплет позволяет проверить три разных результата:

| Эксперимент | Цель | Практический результат |
| --- | --- | --- |
| `rare` | Войти в `targetRare()` | Найти 8 подходящих наборов из восьми входных байтов |
| `overflow` | Войти в `targetOverflow()` | Найти суммы, при которых переполнение обходит проверку лимита |
| `impossible` | Войти в `targetImpossible()` | Установить, что условия перед вызовом несовместимы |

«Войти в метод» означает, что исполнение дошло до его начала. Это ещё не ответ
апплета. Поэтому скрипт дополнительно продолжает найденный путь до завершения
команды и повторяет найденный запрос с конкретными байтами.

## 2. Самый короткий путь к результату

1. Установите дополнение из `symdemo_execution_guide_update.zip` поверх проекта
   с исправлениями D-01–D-08. Распаковывайте рядом с `main.py`, сохраняя каталоги.
2. Убедитесь, что присланные файлы сборки лежат в `examples/symdemo/`.
3. Из корня проекта выполните:

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py all
```

Ожидаемые существенные строки:

```text
install: OK; applet AID F053594D44454D4F00
inspect: methods=11; ready=11; unresolved=0
rare: reached; found=1; active=0; errors=0; complete=True
overflow: reached; found=1; active=0; errors=0; complete=True
impossible: unreachable_in_model; found=0; active=0; errors=0; complete=True
```

Отчёты появятся в `outputs/symdemo_execution/`. Дальше разберём, почему нужны
именно эти файлы и что означает каждая часть результата.

## 3. Какие файлы нужны и для чего

| Файл | Откуда он появляется | Как используется |
| --- | --- | --- |
| `examples/symdemo/symdemo.cap` | Результат Java Card Converter | Основной вход: из него берутся байткод, подписи, импорты, классы и сведения об апплете |
| `examples/symdemo/symdemo.java` | Исходный код апплета | Нужен человеку для объяснения проверок и сопоставления целей с исходным кодом |
| `examples/symdemo/symdemo.jca` | Текстовый вывод Converter | Помогает сопоставить имена, ссылки constant pool, инструкции и методы CAP |
| `examples/symdemo/symdemo.exp` | Экспортные сведения пакета | Полезен для проверки сборки и межпакетных ссылок; в данном запуске напрямую не читается |
| `examples/symdemo/symbols.json` | Подготовлен для этой сборки по CAP и JCA | Связывает числовые идентификаторы CAP с именами классов и методов |
| `angr_integration/symdemo_api.py` | Дополнение среды | Описывает семь разрешённых внешних вызовов framework 1.6 |
| `run_symdemo.py` | Скрипт эксперимента | Загружает программу, выполняет install, создаёт входы, ищет цели и пишет результаты |

**Исполняется программа, полученная из CAP.** Java-файл не компилируется во время
анализа и не заменяет CAP. JCA не используется как альтернативный исполняемый
код. Скрипт читает готовый `symbols.json`; он не генерирует его автоматически
при каждом запуске. Присутствие EXP само по себе также не создаёт API-модели.

В дополнение не включены повторные копии ваших четырёх входных файлов, виртуальная
среда и папка outputs. Основная документация проекта `PROJECT.md` остаётся общей;
этот отдельный гайд посвящён конкретному примеру.

## 4. Что действительно получилось после сборки

Не ориентируйтесь на оставшиеся в Java-комментарии предложенные имена и AID.
Для запуска существенны фактические данные сборки:

| Параметр | Значение | Источник |
| --- | --- | --- |
| Java-класс | `symdemo.symdemo` | `package symdemo` и `class symdemo`, подтверждены JCA |
| Версия формата CAP | `2.2` | Header.cap |
| AID пакета | `F053594D44454D4F` | Header.cap, секция `.package` JCA |
| Версия пакета | `1.0` | Header.cap, JCA |
| AID апплета | `F053594D44454D4F00` | Applet.cap, секция `.applet` JCA |
| Import framework | `a0000000620101@1.6` | Import.cap, секция `.imports` JCA |
| Import java.lang | `a0000000620001@1.0` | Import.cap, JCA |
| Количество методов | `11` | Descriptor.cap и извлечённые методы |

В частности, суффикс AID — `00`, а не предложенный раньше `01`. Имя класса —
`symdemo.symdemo`, а не `symdemo.SymbolicDemoApplet`.

Контрольная сумма CAP:

```text
29e72750b5662cb3a71ce035c829f73c8de2b722114dbef968a14c512cab06fa
```

Её можно проверить:

```powershell
Get-FileHash .\examples\symdemo\symdemo.cap -Algorithm SHA256
```

Скрипт проверяет эту сумму перед использованием привязок. После пересборки
смещения методов могут измениться. Поэтому другой CAP требует пересмотра
`symbols.json` и контрольной суммы; простое удаление проверки не обновляет адреса.

## 5. Откуда берётся symbols.json

В CAP многие ссылки записаны числами. Имя `targetRare` удобно человеку, но
внутренний вызов в CAP ссылается на метод по смещению. Таблица символов связывает
эти два представления.

Для данного пакета начало ключа всегда `f053594d44454d4f@1.0`. Например:

```json
"f053594d44454d4f@1.0:internal:t6:o597": "targetRare"
```

Здесь `o597` — смещение заголовка метода относительно info-части Method component.
Это не Java-строка и не смещение внутри тела метода. `t6` обозначает вид CAP-ссылки;
он сам по себе не означает, что Java-метод объявлен static. Private instance
methods тоже могут вызываться через такую внутреннюю ссылку.

Проверенное соответствие:

| Имя | Смещение метода | Что делает |
| --- | ---: | --- |
| `<init>` | 1 | Конструктор |
| `install` | 8 | Создаёт и регистрирует экземпляр |
| `process` | 30 | Проверяет заголовок и выбирает команду |
| `receiveExact` | 137 | Проверяет Lc и фактически принятый размер |
| `runRare` | 182 | Проверяет восемь байтов |
| `runOverflow` | 430 | Выполняет вычисление с ошибочной проверкой лимита |
| `runImpossible` | 522 | Проверяет несовместимые условия |
| `targetRare` | 597 | Возвращает маркер `10 01` |
| `targetOverflow` | 608 | Возвращает маркер `20 01` |
| `targetImpossible` | 619 | Вернул бы `30 01`, если бы был достигнут |
| `sendResult` | 630 | Записывает два байта ответа |

Смещения взяты из Descriptor/Method, имена и вызовы сверены с JCA. У private
методов Descriptor token равен `255` и повторяется: нельзя использовать его как
уникальный номер метода. Для этого примера уникальна комбинация пакета и offset.

У внешних ссылок другая структура. В JCA есть:

```text
virtualMethodRef 0.10.6()S; // setIncomingAndReceive()S
```

`0` — индекс импорта framework; `10` — token класса APDU; `6` — token метода;
`S` — short в сигнатуре возвращаемого значения. Соответствующий ключ:

```text
a0000000620101@1.6:c10:t3:m6
```

Номер этой записи в constant pool — отдельная величина. Его нельзя подставлять
вместо token метода. Имена внешних классов и методов записаны в `symbols.json`,
а поведение вызовов определяется API-профилем. Эти две задачи различаются.

Пустой `interface_signatures` здесь корректен: апплет не вызывает интерфейсные
методы вроде `DESKey.setKey`. Статические константы Java подставлены в байткод;
данная сборка не требует моделировать mutable static fields.

## 6. Зачем понадобился профиль symdemo

Существующий профиль `name1` сопоставляет API по точному ключу с версией `1.5`.
Присланный CAP импортирует framework `1.6`. Даже одинаковое имя метода не
разрешает молча изменить версию его идентификатора.

Новый профиль явно разрешает только следующие вызовы данной сборки:

| Метод | Что делает модель среды |
| --- | --- |
| `Applet.<init>()` | Фиксирует создание объекта во время install |
| `Applet.register(byte[], short, byte)` | Регистрирует экземпляр под переданным AID |
| `Applet.selectingApplet()` | Возвращает флаг, заданный при подготовке команды |
| `APDU.getBuffer()` | Возвращает ссылку на APDU-буфер |
| `APDU.setIncomingAndReceive()` | Переносит заданный вход в буфер и возвращает размер первого приёма |
| `APDU.setOutgoingAndSend(short, short)` | Сохраняет указанные байты ответа |
| `ISOException.throwIt(short)` | Завершает команду с указанным SW |

Реализации lifecycle/APDU переиспользуются из существующей среды, но набор
ключей профиля отдельный. Криптографические модели не включаются, PyCryptodome
этому примеру не требуется. Это не общая поддержка всех API framework 1.6.

## 8. Что делает общий конвейер main.py

Чтобы получить все промежуточные представления:

```powershell
.\.venv-angr10\Scripts\python.exe main.py --cap examples/symdemo/symdemo.cap --symbols examples/symdemo/symbols.json --output-root outputs/symdemo_pipeline --javacard-profile symdemo --no-png --quiet
```

Этапы происходят последовательно:

| Этап | Простое объяснение | Где смотреть |
| --- | --- | --- |
| CAP parsing | Прочитать компоненты и выделить методы | Входной CAP, проверка количества методов |
| CFG | Разбить метод на блоки и связать возможные переходы | `cfg_output/*.txt` |
| JCVM IR | Представить инструкции с типами и стековой семантикой | `ir_output/*.txt`, `*.json` |
| JVM-like IR | Заменить неявный стек явными значениями | `jvm_ir_output/*.txt`, `*.json` |
| Soot IR | Подготовить переменные, выражения и переходы для Java-движка | `soot_output/*.jimple`, `program.json` |
| pysoot | Создать реальные объекты модели, понятные angr | `pysoot_output/program.json` |
| angr loader | Создать проект, адреса и проверить доступность исполнения | `angr_output/load_report.txt`, `addresses.json` |

Каталоги в таблице находятся внутри `outputs/symdemo_pipeline/`.
Например, `method_4` в этом экспорте соответствует `runRare`: это индекс в
экспортируемом списке, а не CAP token или method offset. Надёжное соответствие
проверяйте по имени/ключу внутри файла.

В конце main.py выведет 11 методов и вход `...:internal:t6:o8`, то есть install.
Сообщение «Исполнение апплета не запускалось» нормально: команда выполнила
преобразования и загрузку. Для экспериментов далее нужен `run_symdemo.py`.

Вариант только до Soot, без зависимостей angr/pysoot:

```powershell
.\.venv-angr10\Scripts\python.exe main.py --cap examples/symdemo/symdemo.cap --symbols examples/symdemo/symbols.json --output-root outputs/symdemo_ir_only --no-pysoot --no-png --quiet
```

У него намеренно отсутствует `--javacard-profile`: профиль относится к angr.
Сам по себе `main.py --no-png` по-прежнему использует стандартный `example.cap`;
появление папки symdemo не меняет глобальные defaults main.py.

## 9. Как устроен APDU в этом примере

Команда содержит заголовок, длину, данные и ожидаемую длину ответа:

| Поле | Значение | Смысл |
| --- | --- | --- |
| CLA | `80` | Класс команд демонстрационного апплета |
| INS | `10`, `20` или `30` | Выбор сценария |
| P1, P2 | `00 00` | Дополнительные параметры, здесь должны быть нулевыми |
| Lc | `08` либо `02` | Число байтов DATA |
| DATA | 8 либо 2 байта | То, что проверяет выбранный сценарий |
| Le | `02` | Ожидаем два байта ответа |

Все байты в APDU записаны шестнадцатерично. В таблицах сумм ниже числа обычно
десятичные. Например, данные `0A D0` обозначают число `10 * 256 + 208 = 2768`.

`JavaCardSession.prepare_command` получает поля по отдельности, вычисляет Lc из
длины DATA и создаёт APDU-буфер. Полный текст команды в отчёте удобен для повторения.
В `packet_without_le_hex` нет Le; в `case4_apdu_hex` добавлен завершающий `02`.
Эта версия среды не моделирует транспортную обработку Le, T=0/T=1 или кардридер.
Добавленный Le не является ещё одной символьной переменной и не входит в DATA.

Ответ состоит из данных и статусного слова SW. Например, `20 00 90 00` означает
два байта данных `20 00` и SW `9000`. В JSON они разделены: `response_hex: "2000"`,
`sw: "9000"`. Значение `2000` здесь не является статусным словом.

## 10. Сначала обычный запуск с конкретными байтами

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py concrete --ins 20 --data "00 01"
```

Это команда `80 20 00 00 02 00 01 02`, пополнение на единицу.
Ожидаются `response_hex=2000`, `sw=9000`, отсутствие errors и active paths.

Скрипт сначала действительно исполняет install и конструктор из CAP. Register
записывает AID `F053594D44454D4F00`, после чего сессия получает экземпляр и вход
в `process(APDU)`. Создание экземпляра не подменено заранее готовым объектом.

Флаг `selectingApplet` по умолчанию false: мы исследуем прикладную команду после
установки. Это заданный контекст модели, а не переданная физической карте SELECT
APDU. Сессия не соединяется со смарт-картой.

## 11. Эксперимент rare: найти вход для цепочки проверок

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py rare
```

В этом запуске CLA/INS/P1/P2 зафиксированы как `80 10 00 00`, Lc=8, received_len=8,
selectingApplet=false. Символьны только восемь байтов DATA. Скрипт не ограничивает
их заранее константами из проверок апплета: условия появляются при исполнении CAP.

Подходящий минимальный по значению целого пакета запрос:

```text
80 10 00 00 08 21 BB E3 4C 97 66 D0 0D 02
```

Ответ при продолжении найденного пути и при конкретном повторении: `10 01 90 00`.

Первые данные `21 BB` — это 33 и 187, их сумма равна 220. Следующие зависимые
условия связывают все восемь байтов. Для пути к цели одновременно должны быть верны:

```text
a + b = 220
b XOR c = 0x58
c + d = 303
d XOR e = 0xDB
e + f = 253
f XOR g = 0xB6
g + h = 221
a XOR h = 0x2C
a + b + c + d + e + f + g + h = 997
```

Здесь каждый символ — беззнаковое значение одного входного байта, 0..255.
Промежуточные суммы этого сценария помещаются в положительный short.

В отчёте `rare.json` будет `found=1`, но подходящих DATA восемь:

| № | DATA, hex |
| ---: | --- |
| 1 | `21 BB E3 4C 97 66 D0 0D` |
| 2 | `25 B7 EF 40 9B 62 D4 09` |
| 3 | `27 B5 ED 42 99 64 D2 0B` |
| 4 | `2B B1 E9 46 9D 60 D6 07` |
| 5 | `A1 3B 63 CC 17 E6 50 8D` |
| 6 | `A5 37 6F C0 1B E2 54 89` |
| 7 | `A7 35 6D C2 19 E4 52 8B` |
| 8 | `AB 31 69 C6 1D E0 56 87` |

Это один путь с восемью решениями его условий. `found` считает состояния/пути,
а не конкретные APDU. Скрипт запросил до девяти решений и получил восемь;
`enumeration_complete=true` подтверждает завершённый поиск и отсутствие девятого.

Проверка конкретного найденного входа:

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py concrete --ins 10 --data "21 BB E3 4C 97 66 D0 0D" --output-root outputs/symdemo_rare_replay
```

Преимущество видно в размере пространства: восемь произвольных байтов дают
2^64 комбинаций. При равномерном независимом случайном выборе вероятность
попасть в одну из восьми — 8/2^64. Символьное исполнение получает ограничения
из кода и решает их. Это сравнение с простым случайным перебором, не измерение
скорости и не утверждение о превосходстве над любым направленным fuzzing.

## 12. Эксперимент overflow: найти ошибку проверки лимита

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py overflow
```

Фиксированы заголовок `80 20 00 00`, Lc=2 и полный приём. Оба байта DATA неизвестны.
Из них апплет собирает short amount и допускает положительные суммы до 10000.

Ошибка в следующем порядке действий:

```java
short proposed = (short) (START_BALANCE + amount);
if (proposed > BALANCE_LIMIT) {
    ISOException.throwIt(ISO7816.SW_CONDITIONS_NOT_SATISFIED);
}
```

Начальный баланс — 30000, лимит — 32000. Для amount=2768 математическая сумма
равна 32768. После приведения к 16-битному знаковому short получается -32768.
Отрицательное число не больше 32000, поэтому проверка пропускает его. Следующее
условие `proposed < 0` ведёт в диагностическую цель `targetOverflow()`.

Найденный минимальный запрос:

```text
80 20 00 00 02 0A D0 02
```

Ожидаемый ответ: `20 01 90 00`. Сам SW=9000 здесь не доказывает корректность
бизнес-логики: данные `20 01` сообщают, что произошёл ошибочный сценарий.

Полный найденный диапазон — **2768..10000 включительно**, то есть 7233 значения.
Он проверен в обе стороны сравнением условий найденных путей с этим интервалом.
Один лишь минимум и максимум не доказывали бы отсутствие «дыр» внутри диапазона.

| amount, десятичное | DATA | Результат | Почему |
| ---: | --- | --- | --- |
| 0 | `00 00` | SW `6A80` | Сумма должна быть положительной |
| 1 | `00 01` | `20 00 90 00` | Баланс 30001 допустим |
| 2000 | `07 D0` | `20 00 90 00` | Баланс ровно 32000 |
| 2001 | `07 D1` | SW `6985` | Баланс больше лимита, переполнения ещё нет |
| 2767 | `0A CF` | SW `6985` | 32767 ещё положителен |
| 2768 | `0A D0` | `20 01 90 00` | Первая сумма с переполнением |
| 10000 | `27 10` | `20 01 90 00` | Допустимый amount, переполненный результат |
| 10001 | `27 11` | SW `6A80` | Сумма выше MAX_AMOUNT |
| 32768 в исходных двух байтах | `80 00` | SW `6A80` | При разборе amount становится отрицательным short |

Повторение контрпримера:

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py concrete --ins 20 --data "0A D0" --output-root outputs/symdemo_overflow_replay
```

Здесь видна польза учёта машинной арифметики. Анализ с математическими целыми
без 16-битного переполнения не воспроизвёл бы данный обход.
Сам апплет намеренно оставлен с ошибкой: исправление проверяемой программы
сейчас уничтожило бы демонстрационный пример.

## 13. Эксперимент impossible: чем доказательство отличается от неудачного поиска

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py impossible
```

Ожидается:

```text
impossible: unreachable_in_model; found=0; active=0; errors=0; complete=True
condition equivalence: True
```

Перед целью требуются одновременно:

```text
x + y = 300
x XOR y = 138
x AND y = 65
```

Для этих неотрицательных значений верно тождество:

```text
x + y = (x XOR y) + 2 * (x AND y)
```

Последние два условия дают 138 + 2*65 = 268, что противоречит 300.
Переполнение тут не помогает: x и y находятся в 0..255, их сумма не больше 510.

Каждая пара условий имеет решения, но вся тройка — нет. Поэтому нельзя делать
вывод о достижимости по отдельным if. Нужна совместная проверка пути.

Формулировка `unreachable_in_model` относится к данному CAP, профилю среды и
зафиксированному контексту. Скрипт делает её только после завершения всех путей,
без активных состояний, ошибок и других необработанных групп состояний.
Это не следствие того, что за некоторое время не удалось найти удачный запрос.

## 14. Найти ещё и заголовок команды

В первых экспериментах INS задавался заранее: мы искали DATA для выбранной команды.
Чтобы решатель сам определил CLA, INS, P1 и P2:

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py rare --symbolic-header --output-root outputs/symdemo_header
```

Теперь символическими становятся четыре байта заголовка и восемь DATA.
Длина остаётся конкретной: Lc=8. Для достижения targetRare найденные команды
по-прежнему начинаются с `80 10 00 00 08`, но теперь ограничения на заголовок
получены из исполнения process, а не заданы начальными значениями.

Это важное различие при изложении результатов: нельзя писать, что анализ нашёл
INS, если INS был заранее передан как константа.

## 15. Как начальный контекст меняет ответ

Одни и те же DATA не определяют весь результат. Важны состояние апплета, выбор
команды, длина и приём. Три полезных контрольных запуска:

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py rare --selecting --output-root outputs/symdemo_selecting
.\.venv-angr10\Scripts\python.exe run_symdemo.py rare --length 7 --output-root outputs/symdemo_length7
.\.venv-angr10\Scripts\python.exe run_symdemo.py rare --receive-length 7 --output-root outputs/symdemo_partial
```

Во всех случаях цель недостижима в выбранном контексте, но причины различаются:

- `--selecting`: process возвращается сразу после selectingApplet().
- `--length 7`: Lc=7, а команда требует восемь байтов.
- `--receive-length 7`: Lc=8, но первый приём вернул только семь байтов.

Последние два случая завершаются SW=6700. Мы не утверждаем, что targetRare
недостижим вообще: выше уже найден вход при другом контексте.

Ограничение числа шагов проверяется отдельно:

```powershell
.\.venv-angr10\Scripts\python.exe run_symdemo.py rare --max-steps 1 --output-root outputs/symdemo_cutoff
$LASTEXITCODE
```

Ожидаются `unknown`, `active` больше нуля, `complete=False` и exit code `2`.
Install получает отдельный достаточный бюджет; здесь намеренно ограничен поиск.
Повтор с `--max-steps 500` завершает этот пример. Шаг — итерация движка анализа,
не обязательно одна инструкция JCVM и не заданное число секунд.

## 16. Как читать JSON-отчёты

| Поле | Значение |
| --- | --- |
| `cap_sha256` | Какой именно двоичный CAP исследован |
| `target_key` / `target_address` | Идентификатор цели и её адрес в модели angr |
| `context` | Фиксированные условия эксперимента |
| `symbolic` | Какие байты действительно оставлены неизвестными |
| `search.found` | Число состояний, дошедших до входа в целевой метод |
| `search.deadended` | Остальные завершившиеся состояния, не обязательно ошибки |
| `search.active` | Незавершённые пути |
| `search.errors` | Ошибки исполнения/модели; это не SW апплета |
| `search.complete` | Исследование всех оставшихся путей завершено без ошибок |
| `found_path_constraints` | Условия каждого найденного пути |
| `condition_equivalence_checked` | Независимая проверка совпадения найденного множества входов с объясняющей формулой |
| `packet_without_le_hex` | Один совместно найденный пакет без Le |
| `case4_apdu_hex` | Тот же пакет с добавленным Le=02 |
| `continuations` | Что произошло после продолжения найденных состояний |
| `replay` | Что произошло при отдельном запуске уже конкретного запроса |
| `matching_apdus` | До девяти решений rare; в этой сборке их восемь |

SW `6985` или `6700` — обычный исход программы. Он может находиться среди
завершённых путей и не увеличивает `errors`. Ошибка неподдержанной инструкции,
неизвестного API либо модели памяти — уже ошибка среды, её нельзя трактовать
как доказанный ответ апплета.

Один найденный путь может быть достоверным свидетелем даже при незавершённых других
путях. Но полный список решений и недостижимость требуют законченного исследования.
Exit code `2` используется, если поиск/продолжение не закончены, есть ошибки или
обнаружено несовпадение с проверочной формулой. Обычная недостижимая цель при
завершённом исследовании даёт exit code `0`.

В формулах встречаются SignExt, срезы битов и Reverse. Это низкоуровневое
представление значений движком. Например, SignExt относится к знаковому расширению.
Для понимания причины пути сначала смотрите исходную проверку и числовые поля
отчёта. Длинная строка solver constraints полезна для отладки реализации.

## 17. Как связаны Java-строка, CAP offset и Soot Unit

Номера строк относятся только к присланному Java-файлу. Основная цель скрипта —
вход в метод по CAP-идентичности, поэтому добавление комментария не меняет
смысла поиска. Это не универсальный Java source-line debugger.

| Цель | Java-строка вызова | Вызывающий метод | Offset вызова внутри его байткода | Soot Unit | Offset метода-цели |
| --- | ---: | --- | ---: | ---: | ---: |
| targetRare | 137 | runRare | 242 | 189 | 597 |
| targetOverflow | 158 | runOverflow | 77 | 58 | 608 |
| targetImpossible | 181 | runImpossible | 69 | 57 | 619 |

Пример: вызов targetRare находится на offset 242 внутри тела runRare. Сам runRare
имеет ключ с `o182`, а targetRare — с `o597`. Это три разные координаты.
Unit — номер инструкции в Soot-представлении данного метода, не номер CAP opcode.

Таблица получена сопоставлением присланного Java/JCA и `callsites` текущего
загрузчика. Автоматическое чтение Java line table из Debug.cap этим скриптом
не реализовано. После пересборки offsets/Units нужно получить заново.

## 18. Что происходит внутри run_symdemo.py

Работа организована в следующем порядке:

1. `load_symdemo()` проверяет CAP hash и привязки имён, запускает обычные стадии
   конвейера и подключает профиль symdemo.
2. `new_session()` исполняет install и получает зарегистрированный экземпляр.
3. `analyze()` создаёт отдельные восьмибитные переменные DATA через Claripy BVS.
4. `prepare_command()` помещает заголовок и вход в модель APDU и создаёт вызов process.
5. Менеджер состояний исполняет блоки. Перед каждой итерацией состояния на входе
   в target переносятся из active в found. Остальные продолжаются до завершения.
6. Условия всех found объединяются. Решатель выбирает один целый пакет и, для rare,
   перечисляет все решения. Нельзя независимо выбирать минимум каждого байта:
   такие минимумы могут принадлежать разным несовместимым решениям.
7. Выполняются продолжение, конкретный replay и независимая проверка условий.

Ключевой фрагмент подготовки входа выглядит так:

```python
from run_symdemo import load_symdemo, new_session

loaded = load_symdemo()
session = new_session(loaded)
claripy = loaded.dependencies.claripy
data = tuple(claripy.BVS(f"DATA_{i}", 8, explicit_name=True) for i in range(8))
state = session.prepare_command(0x10, data=data, cla=0x80,
                                selecting=False, receive_length=8)
```

Здесь BVS не выбирает случайный байт: это переменная с 256 возможными значениями.
В закреплённой версии проекта Claripy доступен как `angr.claripy`; приведённый
публичный доступ через loaded.dependencies не требует отдельного `import claripy`.

Полный анализ из собственного Python-кода:

```python
from run_symdemo import load_symdemo, new_session, analyze, fully_checked

loaded = load_symdemo()
session = new_session(loaded)
report = analyze(session, "rare", max_steps=500)
assert fully_checked(report), report
print(report["reachability"])
print(report.get("case4_apdu_hex"))
```

`expected_condition()` содержит объясняющую математическую формулу для контроля
результата. Она применяется после исследования: скрипт проверяет невозможность
расхождения между найденными путями и формулой в обе стороны. Эта формула не
добавляется к начальному состоянию и не подсказывает движку заранее нужный вход.

`JavaCardSession.run()` не выбирает один исход как новое состояние сессии. В этих
экспериментах команды стартуют из состояния после install; у апплета нет изменяемого
прикладного состояния. Для другого, stateful апплета понадобится отдельное решение
о последовательности команд и выборе завершённого состояния через choose/transmit.

## 22. Какие границы имеет вывод

Результат относится к конкретному CAP и явно выбранным Python-моделям API.
Прошивка физической карты, GlobalPlatform, транспорт, защита каналов и полный
Java Card Runtime здесь не исполняются. Общий Java dispatch catch-обработчиков
не реализован; у данного апплета нет таких обработчиков.

Модель использует short APDU, один апплет/канал и первый приём данных. Lc и
received_len — конкретные параметры, а не символьная длина массива. Метод
setIncomingAndReceive по API сообщает число фактически принятых байтов; наш
апплет явно отвергает частичный приём. Для фрагментированного обмена понадобятся
другой код апплета и модель дополнительных API.

Успех этих опытов не означает, что любой Java Card CAP уже поддерживается.
Для нового апплета нужно проверить импортированные API, типы, инструкции,
состояние после install и соответствующие модели. Имена и контрольная сумма
данного примера не переносятся на другой бинарный файл.

Для диплома эти три опыта дают разные проверяемые результаты: генерацию входов
для редкой ветки, конкретный контрпример с переполнением и обоснованную
недостижимость противоречивой цели в зафиксированном контексте.

- [Oracle: APDU API](https://docs.oracle.com/cd/E59935_01/api/javacard/framework/APDU.html) — буфер, приём данных и отправка ответа.
- [Oracle: JCVM Specification 3.0.5](https://docs.oracle.com/cd/E59935_01/JCVMS.pdf) — компоненты CAP, ссылки и инструкции. Версии импортированных пакетов в этом опыте установлены по самому CAP/JCA.
