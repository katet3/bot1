# verification_engine — структурные правила CFG

[К документации](../README.md) · [Фасад](../../verification_engine/verifier.py)

## Назначение и API

Рабочий публичный вызов — `Verifier().verify(method)`. Он сам строит CFG через
`cfg_generator.builder.build_cfg`, затем передаёт его в `RuleEngine.run(cfg)`.
Старое описание `VerificationEngine.verify(method, cfg)` не соответствует коду.
Чтобы проверить заранее созданный CFG, можно явно использовать `RuleEngine`;
готовый фасад `Verifier` такой параметр не принимает.

Проверка является набором структурных правил. Стек, типы значений, байтовое
покрытие метода и точное соответствие семантике переходов проверяются позднее
другими модулями. Этот пакет не сравнивает граф с внешним эталонным графом.

## Структура и поток данных

`RuleEngine` один раз строит `RuleContext`: block map, исходный edge list,
adjacency и reverse adjacency. Правило реализует `check(cfg, context)` и возвращает
список `VerificationError`. Engine добавляет его через `report.extend(errors)`:
диагностики сохраняются плоским списком в порядке правил и в порядке внутри
каждого результата. `VerificationReport` хранит success/errors, умеет
extend/merge и вывод в текст. Поле `severity` базового `Rule` сейчас не управляет
успехом отчёта: наличие добавленной ошибки делает success ложным.

Контекст разделяет исходные данные и индексы обхода:

- `edge_list` сохраняет все исходные рёбра, в том числе с отсутствующими концами;
- ключи `block_map`, `adjacency` и `reverse_adjacency` — только ID объявленных блоков;
- ребро включается в оба индекса соседства только при существовании обоих концов;
- порядок и кратность корректных рёбер сохраняются; исходный CFG не изменяется.

Отсутствующий блок не создаётся через `setdefault`. `EdgeTargetRule` проверяет
полный `cfg.edges`, поэтому исключение ребра из индекса не скрывает нарушение.
Контекст безопасно доступен и правилам, которые запускаются раньше EdgeTargetRule.

| Модуль | Определения | Фактическое поведение |
| --- | --- | --- |
| `verifier.py` | `Verifier` | Регистрирует четыре правила и строит CFG |
| `engine/rule_base.py` | `Rule` | Абстрактный `check`, name, severity |
| `engine/rule_context.py` | `RuleContext` | Индексы, общие для всех правил |
| `engine/rule_engine.py` | `RuleEngine` | Построение context и последовательный запуск rules |
| `model/verification_error.py` | `VerificationError` | Тип ошибки называется `error_type`, плюс message и необязательные координаты |
| `model/verification_report.py` | `VerificationReport` | `add_error`, `extend`, `merge`, `has_errors`, `summary`, `to_text` |
| `rules/block/empty_block_rule.py` | `EmptyBlockRule` | Проверка непустых instructions |
| `rules/graph/reachability_rule.py` | `ReachabilityRule` | Единственная entry и BFS достижимости всех блоков |
| `rules/edge/edge_target_rule.py` | `EdgeTargetRule` | Проверка наличия source/target в block map |
| `rules/consistency/successor_rule.py` | `SuccessorConsistencyRule` | Сравнение множества block.successors с adjacency |
| `rules/block/overlap_rule.py` | Нет | Пустая заготовка; overlap не проверяется этим правилом |
| `rules/block/range_rule.py` | Нет | Пустая заготовка; range rule отсутствует |
| `rules/consistency/predecessor_rule.py` | Нет | Пустая заготовка; отдельная симметричная проверка predecessors отсутствует |
| `rules/edge/conditional_rule.py` | Нет | Пустая заготовка |
| `rules/edge/exit_rule.py` | Нет | Пустая заготовка |
| `rules/graph/entry_rule.py` | Нет | Пустая заготовка; часть проверки entry находится в ReachabilityRule |
| `tests/test_cfg_rules.py` | `CFGRuleTests` | 15 регрессий контракта диагностики четырёх правил, включая корректные и ошибочные CFG |
| `tests/test_rule_engine.py` | `RuleEngineTests` | 10 регрессий агрегации, количества и текста ошибок, независимости отчётов и merge |
| `tests/test_invalid_edges.py` | `InvalidEdgeTests` | 10 регрессий повреждённых рёбер через RuleEngine, индексов соседства и сохранности CFG |

SuccessorConsistency использует множества: он проверяет состав целей, но не
кратность рёбер и не различие TRUE/FALSE. Reachability включает рёбра с обоими
существующими концами, в том числе exceptional, если они построены upstream.
При повреждённом графе достижимость определяется по этому подграфу; несуществующий
блок не может служить промежуточной вершиной между двумя реальными блоками.
`block.successors` не исправляется автоматически: лишняя несуществующая цель
может дополнительно дать `SUCCESSOR_MISMATCH`.

## Контракт диагностики и технический долг

D-01 исправлен: все пять неверных вызовов конструктора в четырёх правилах
используют `VerificationError(error_type=..., message=...)`. Контракт dataclass
и значения типов ошибок сохранены; псевдоним `code` не добавляется.

D-02 исправлен: `RuleEngine.run` использует `report.extend(errors)` для списка.
`add_error` сохраняет свой контракт добавления одного `VerificationError`.
Число ошибок в `summary()` теперь отражает число диагностик, а `to_text()`
выводит каждую из них отдельной строкой. `merge()` объединяет такие отчёты
без вложенных списков. Изменения dataclass или класса отчёта не потребовались.

D-03 исправлен: `_build_context` проверяет наличие обоих концов перед добавлением
ребра в индексы. Отсутствующий источник и/или цель дают `INVALID_EDGE_SOURCE`
и/или `INVALID_EDGE_TARGET` через обычное правило. Проверка не зависит от
порядка правил; их регистрация и порядок диагностики сохраняются.

Это не полная проверка произвольного объекта вместо CFG или всех вариантов
повреждённого CAP. В частности, построение CFG из байткода и согласование handlers
выполняются раньше, в других модулях. `report.success=True` означает отсутствие
срабатывания зарегистрированных правил, а не доказанную корректность программы.

## Регрессионные проверки D-01–D-03

Из корня проекта:

```powershell
.\.venv-angr10\Scripts\python.exe -m unittest discover -s verification_engine/tests -p "test_*.py" -v
```

Тестам достаточно стандартной библиотеки Python и исходников проекта; angr,
pysoot, Graphviz и CAP-фикстуры не нужны. До исправления D-01 9 из 15 тестов правил
падали с `unexpected keyword argument 'code'`. До исправления D-02 падали 6 из
10 тестов агрегации. До исправления D-03 8 из 10 тестов повреждённых рёбер
падали с `KeyError`. После трёх исправлений все 35 тестов проходят.

Проверяются пустые блоки, отсутствие/множественность entry, пустой граф,
недостижимые блоки, отсутствующие концы рёбер и несовпадающие successors.
Для каждого случая проверяются тип объекта, `error_type`, сообщение и текстовое
представление; корректные графы не должны давать ложных ошибок.

В наборе D-01 ошибочные случаи запускают `rule.check(cfg, context)` с явным `RuleContext`.
Текст отчёта проверяется через существующий `VerificationReport.extend`,
а корректный граф — дополнительно через `RuleEngine`. Такое разделение проверяет
D-01 независимо от построения context на повреждённых рёбрах (D-03).

Набор D-02 дополнительно вызывает RuleEngine с несколькими правилами и несколькими
ошибками каждого правила. Проверяются порядок, плоский тип элементов, точное
число ошибок и текст отчёта, пустые результаты, повторные запуски и объединение
отчётов. Отдельный CFG с корректными концами рёбер даёт четыре нарушения через
реальные правила; они должны остаться четырьмя отдельными ошибками в отчёте.

Набор D-03 запускает повреждённые графы через `RuleEngine.run`, включая набор
правил, зарегистрированный в `Verifier`. Проверяются несуществующие source/target,
оба отсутствующих конца, рёбра без блоков, смешанные корректные и ошибочные рёбра,
ложный путь через несуществующий блок и неизменность исходных данных. Корректные
циклы, петли, параллельные рёбра и непоследовательные ID продолжают работать.

## Как добавлять правило

Наследуйте `Rule`, возвращайте список `VerificationError(error_type=..., message=...)`,
используйте готовый context и зарегистрируйте правило в `Verifier.__init__`.
Для обхода используйте индексы соседства; для проверки исходных рёбер —
`cfg.edges` или `context.edge_list`. Полный список может содержать ссылки на
отсутствующие блоки: перед обращением к `block_map` правило должно проверить членство.

Для каждого правила нужны корректный граф и минимальный граф-нарушитель.
Отдельно проверяются точный error_type, заполняемые правилом координаты, плоский errors list и то,
что вывод `to_text()` остаётся пригодным для главного CLI. При проверке source/target
порядок обработки должен гарантировать, что диагностика достижима на повреждённом
графе. Проверяйте новое правило как напрямую, так и через RuleEngine.
