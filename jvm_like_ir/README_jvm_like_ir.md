# JVM-like IR для cap2soot

Модуль устраняет неявный стек операндов JCVM и строит типизированные операции с явными
значениями. Это промежуточная модель для следующего Soot lowering. Она пока не является
Jimple/Shimple, JVM class file или движком символьного исполнения.

## Интеграция с main.py

Добавьте импорт:

```python
from jvm_like_ir import JVMLikeIRBuilder
```

До цикла обработки методов:

```python
jvm_builder = JVMLikeIRBuilder()
jvm_output = Path("jvm_ir_output")
jvm_output.mkdir(exist_ok=True)
```

В цикле после вашего `ir = ir_builder.build(method, cfg=cfg)`:

```python
jvm_ir = jvm_builder.build(ir)

(jvm_output / f"method_{index}.json").write_text(
    jvm_ir.to_json(), encoding="utf-8"
)
(jvm_output / f"method_{index}.txt").write_text(
    jvm_ir.to_text(), encoding="utf-8"
)
```

`ir` — объект `jcvm_ir.MethodIR`, не исходный Method и не CFG. Модуль не изменяет входной
объект и не парсит байткод повторно. `build()` автоматически проверяет выходную модель;
после ручных изменений модели можно отдельно вызвать `jvm_ir.validate()`.

Полный минимальный пример:

```python
from pathlib import Path
from cap_decompile.container.cap_container import CAPContainer
from cap_decompile.model.cap_file import CAPFileBuilder
from jcvm_ir import IRBuilder, ReferenceResolver, methods_from_cap
from jvm_like_ir import JVMLikeIRBuilder

container = CAPContainer(Path("example.cap"))
container.load()
cap = CAPFileBuilder.build(container)
stack_builder = IRBuilder(ReferenceResolver(cap))
value_builder = JVMLikeIRBuilder()

for method in methods_from_cap(cap):
    jcvm = stack_builder.build(method)
    result = value_builder.build(jcvm)
    print(result.to_text())
```

## Результат преобразования

Фрагмент последнего блока метода 5 теперь представлен примерно так (имена временных
значений сокращены для пояснения):

```text
object:reference = local[0]
receiver:reference = local[0]
old:short = load_field(receiver, cp#1)
amount:short = local[5]
updated:short = add<short>(old, amount)
store_field(object, updated, cp#1)
return()
```

Чтения не объединяются оптимизатором: это прямое преобразование с сохранением порядка
операций. `this` становится явным receiver. `dup` повторно использует уже вычисленное
значение, а `pop` удаляет только его использование; вызов или выделение объекта не исчезает.
Константы встраиваются в операнды. `sinc/iinc` раскрываются в load → add → store.

## Модель

| Сущность | Содержание                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `Value`        | Неизменяемое временное значение: уникальное имя и вычислительный тип |
| `Constant`     | Целочисленная константа либо null с типом                                                        |
| `Argument`     | Исходный тип аргумента, его слот JCVM и признак receiver                                      |
| `Statement`    | Явные операнды, результат, операция, source offset, ссылки и обработчики         |
| `Terminator`   | branch, switch, goto, return или throw                                                                                        |
| `Block`        | Параметры блока, statements, terminator и исходные смещения                                       |
| `Edge`         | Вид перехода, аргументы целевого блока, case value или handler index                         |
| `Method`       | Сигнатура, аргументы, размер массива locals, блоки и рёбра                             |

TXT — читаемый обзор. JSON содержит полные CAP references и сигнатуры.
`schema_version=1` относится к этой модели; JSON не загружается обратно этим модулем.

Вычислительные типы значений — `short`, `int`, `reference`. Тип хранения byte/boolean,
массивов, полей и объявленные типы вызовов сохраняются в `semantic_type`, `Reference` и
`Signature`. Например вызов, возвращающий boolean, имеет вычислительный результат short.
Это не удаление исходной сигнатуры. Позиция local — слот JCVM, а не готовый индекс JVM.

## Значения между блоками и циклы

Для каждого значения входного стека создаётся параметр блока. Обычное ребро передаёт
значения выходного стека в соответствующие параметры. Например:

```text
B1():
  goto()
    GOTO -> B3(10)
B2():
  goto()
    GOTO -> B3(20)
B3(%b3_p0:short):
  result:short = add<short>(%b3_p0, 1)
  return(result)
```

Параметры создаются до обработки тел блоков, поэтому обратное ребро цикла может ссылаться
на уже объявленные параметры. Передача аргументов одновременная. В будущем Soot backend
может преобразовать её в parallel copies/отдельные блоки рёбер или в phi-узлы Shimple.

Временные значения имеют единственное определение, но locals остаются изменяемыми слотами.
Это не полная SSA для locals и heap. Чтение local всегда фиксируется во временном значении:
последующая запись в тот же слот не изменяет старое вычисленное значение.

## Проверки

- Аргументы рёбер соответствуют параметрам блоков по количеству и типам.
- Значения определены до использования; между блоками значения доступны только через параметры.
- Операнды арифметики, вызовов, полей, массивов и возвратов имеют нужные типы.
- Порядок receiver и аргументов вызова сохранён.
- Сохранены normal edges, метки switch, ссылки и порядок побочных эффектов.
- Анализ определённости локальных переменных учитывает слияния и циклы.
- Запись в часть двухсловного int делает прежний int недоступным для чтения целиком.
- Нельзя читать неинициализированный local или local с несовместимым вычислительным типом.
- Для исключительного перехода locals берутся в точке бросающей инструкции, до следующих записей.

Ошибки обозначаются `LoweringError`. Неизвестные инструкции не превращаются в пустые операции.
Непосещённый upstream-проверкой блок с `input_stack=None` явно отклоняется: модуль не
придумывает типы его стека. Для такого CAP сначала нужен анализ недостижимого кода/его удаление.

## Арифметический контракт

Семантика операций соответствует JCVM, а не неограниченным целым Python.
`short` — знаковое 16-битное значение, `int` — 32-битное. Арифметика сохраняет разрядность;
операнды некоммутативных операций следуют порядку left, right. Сравнения знаковые, сравнения
reference допускают только eq/ne. Величина сдвига маскируется `& 31`.

`convert.s2b/i2b` сужает до byte и расширяет со знаком до short; `s2i` расширяет со знаком;
`i2s` сужает до short. `compare_signed` выдаёт short -1/0/1.

Для `sushr` генерируется особая последовательность: оба операнда расширяются до int,
выполняется 32-битный логический сдвиг, результат сужается до short. Поэтому `-1 sushr 1`
даёт -1. Обычный 16-битный логический сдвиг дал бы неверное значение 32767.

Деление округляет к нулю, rem согласован с таким частным, деление на ноль — исключение.
Для Soot backend короткую арифметику потребуется выразить подходящими вычислениями/casts.

Нормативный источник: Oracle Java Card VM Specification 3.0.5,
https://docs.oracle.com/cd/E59935_01/JCVMS.pdf , особенно раздел 7.5.107 для sushr.

## Исключения и текущие границы реализации

Сохраняются упорядоченные Handler, catch_type_index, stop_bit и консервативные рёбра JCVM IR.
Каждая потенциально бросающая statement содержит список применимых handler indices.
Исключительное ребро не передаёт старый стек: единственный reference-параметр целевого
блока получает фактически брошенный объект (`@exception` в TXT).

Это описание возможных переходов, а не готовый алгоритм выбора catch. Иерархия исключений,
выбор первого подходящего обработчика, создание исключения при throw null, исключения API
и изменение heap должны быть реализованы/отображены следующим слоем. Консервативный handler
может оказаться недостижимым, если в защищённом блоке нет бросающих операций; в таком случае
анализ locals не объявляет его исполнимым.

Упрощения первой версии: reference без анализа конкретных классов/aliasing; нет проверки
uninitialized object и Java Card firewall; нет SSA для locals/heap; нет оптимизаций и готового
Soot экспорта. Поддержка исходных инструкций ограничена установленным `jcvm_ir`.
`jsr/ret`, invokeinterface и другие неподдержанные upstream-инструкции здесь не добавляются.

## Что проверено

35 тестов нового модуля прошли без пропусков: арифметика, переполнение, signed conversions,
порядок операндов, dup/pop и side effects, непустой стек между блоками, слияния, циклы,
switch, ссылки на receiver, local overlap, обработчики и повреждённая выходная модель.
Мини-исполнитель внутри тестов служит только проверке отдельных числовых примеров;
в публичный модуль не входит symbolic execution engine.

Полная цепочка на вашем `example.cap`: 9 методов, 46 блоков, 52 обычных ребра,
173 statements. Порядок вызовов и операций с памятью и структура CFG сохранены.
В этом CAP нет обработчиков исключений; они проверены синтетическими примерами.

Следующий этап — `soot_ir`: отображение этой модели в выбранное Soot/pysoot представление,
включая block arguments, локальные типы, вызовы и исключительные переходы.
