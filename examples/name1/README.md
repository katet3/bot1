# Тестовый апплет name1

Актуальные руководства: [Java Card runtime](../../docs/modules/javacard_runtime.md), [тесты и фикстуры](../../docs/modules/testing_examples.md), [проект целиком](../../docs/PROJECT.md).

Входные `name1.java`, `name1.jca`, `name1.cap`, `name1.exp` скопированы из
присланного комплекта без изменения байтов. Контрольные суммы всех 18 входных
файлов, включая нативные исходники, находятся в `input_manifest.json`.
Нативные C-файлы остаются справочными входами; они не подключены к angr.

## Что проверено

CAP 2.2 проходит цепочку CAP → CFG → JCVM IR → JVM-like IR → Soot IR → pysoot →
angr.Project. Получены 1 класс, 7 методов, 319 Soot statements, 17 внешних
сигнатур методов. Неразрешённых имён — 0. Последовательности инструкций каждого
метода сверены с независимым JCA, полученным конвертером.

Базовый запуск `main.py` проверяет преобразование и загрузку. Дополнительно
реализовано исполнение `install`, `process`, APDU и конкретных DES ECB/CBC через
явный профиль API. Команда `python -m angr_integration.name1_demo` выполняет 15
сценариев APDU, три символические ветви P1 и отрицательный тест null receiver.
Подробности — [UPDATE_javacard_execution.md](../../UPDATE_javacard_execution.md).
Без выбора профиля API внешние вызовы по-прежнему блокируются.

точную версию SDK 3.0.4. Версии импортируемых пакетов — отдельные идентификаторы.

## Запуск

Из корня проекта, в окружении с `requirements-angr.txt` (Python 3.12+):

```bash
python main.py --cap examples/name1/name1.cap --symbols examples/name1/symbols.json --output-root outputs/name1 --no-png --quiet
python -m unittest integration_tests.test_name1 -v
```

Имена классов, полей и обычных методов в `symbols.json` сопоставлены по JCA.
Сигнатуры обычных вызовов берутся из CAP Descriptor. Для `invokeinterface`
привязка `a0000000620102@1.5:c10:t1:m5` задаёт `DESKey.setKey(byte[], short): void`
по Java и JCA: инструкция содержит Classref #24, токен метода 5 и nargs = 3.
`t1` обозначает исходный тег Classref, а не вымышленную запись methodref в CAP.
Без этой явной сигнатуры конвейер завершится диагностикой.

Это профиль именно присланного CAP. При другой версии импортов, токенах или
повторной сборке внутренние смещения и привязки нужно сверить заново.
`name1.exp` описывает собственный пакет апплета; он не заменяет EXP библиотек API.

## Обнаруженный дефект апплета

Конструктор создаёт только `tempDesKey3`; `tempDesKey2` не присваивается нигде
в Java и CAP. После установки 16-байтового ключа `getDesKey()` выбирает
`tempDesKey2`, то есть `null`. Приведение `null` к DESKey допустимо, но последующий
`invokeinterface setKey` должен вызвать NullPointerException.

В CAP это метод offset 256: `checkcast` по bytecode offset 34 и
`invokeinterface` по offset 41. Проверка подтверждает наличие чтения поля token 4
и отсутствие записи в него. Теперь путь также воспроизведён исполнением CAP в angr
с API-моделями: диагностика `null_reference`, offset 41. На физической карте
в этой среде тест не выполнялся.
Апплет намеренно оставлен неизменным как отрицательный тест. Исправление потребует
создания второго объекта ключа и пересборки Java/CAP/JCA, чтобы комплект оставался
согласованным. Статусное слово при необработанном исключении зависит от JCRE.

## Модели профиля name1

| Методы API | Моделируемое поведение | Присланный ориентир |
| --- | --- | --- |
| `Applet.<init>`, `register(byte[],short,byte)`, `selectingApplet()` | Жизненный цикл, регистрация, признак SELECT | `jc_framework.c`; Java-обёртка конструктора не дана |
| `APDU.getBuffer`, `setIncomingAndReceive`, `setOutgoingAndSend` | Общий буфер, фазы ввода/вывода, фактически принятая длина | `jc_framework_apdu.c` |
| `ISOException.throwIt(short)` | Завершение команды с заданным SW; исключение не возвращает управление как обычный вызов | `jc_framework.c` |
| `Util.arrayCopy(byte[],short,byte[],short,short)` | Границы, перекрытие, возвращаемое смещение, атомарность | `jc_framework.c` |
| `JCSystem.beginTransaction`, `commitTransaction` | Состояние транзакции, запрет вложения, откат при abort | `jc_framework_sys.c` |
| `JCSystem.requestObjectDeletion` | Запрос удаления не является немедленным удалением доступных объектов | `jc_framework_sys22.c` |
| `KeyBuilder.buildKey`, `DESKey.setKey` | Тип/длина ключа, состояние инициализации, transient deselect | `jc_security.c` содержит нижний уровень; публичные Java-обёртки не даны |
| `Cipher.getInstance`, обе `init`, `doFinal` | Идентичность ECB/CBC-объектов, режим, IV, ключ, запись результата в APDU | `jc_crypto.c` содержит CipherImp и вызовы нижнего уровня; полного публичного API нет |

Вызовы конструкторов и приватных instance-методов через `invokespecial`,
виртуальные вызовы, интерфейсный вызов модели DESKey и `srem` теперь исполняются.
Объявления Applet/Key/DESKey/Cipher поставляются явно вместе с API-профилем.
Произвольные внутренние CAP-интерфейсы требуют таблиц сопоставления токенов и
пока отклоняются. Криптография допускает только однозначно определённые данные.

Нативные файлы используют заголовки, функции ядра, транспорт, NVM и менеджер
транзакций, не входящие в комплект. Они полезны как источник поведения моделей,
но не являются готовой автономной библиотекой для загрузки в Soot.
Для точного расширения за пределы этого профиля пригодятся EXP API именно этой
сборки и Java-обёртки KeyBuilder/DESKey/Cipher; текущая интеграция их не требует.

## Первые сценарии APDU

Эти основные сценарии теперь проверяются в `name1_demo`. Предполагаются одна
установка, один логический канал и короткие APDU. Отдельно проверяется частичный
приём: исходник вызывает
`setIncomingAndReceive()` только один раз и не дочитывает остаток.

| Сценарий | INS / P1 / P2 / данные | Ожидаемое по исходнику |
| --- | --- | --- |
| Неверная инструкция | `7F / 00 / 00` | `6D00` после успешного приёма |
| Неверный выбор длины ключа | `20 / 03 / 00` | `6A86` |
| Неверная длина ключа | `20 / 02 / 00`, 16 байт | `6700` |
| Установка 24-байтового ключа | `20 / 02 / 00`, 24 байта | Успех; обновление массива и desKeyLen в транзакции |
| Установка IV | `21 / 00 / 00`, 8 байт | Успех; сохранение IV |
| Неверная длина IV | `21 / 00 / 00`, 7 байт | `6700` |
| Шифрование до установки ключа | `22 / 00 / 00`, 8 байт | `6985` |
| Некратный блоку ввод | `22 / 00 / 00`, 7 байт | `6700` |
| ECB и обратное преобразование | После 24-байтового ключа: `22 / 00 / 00`, затем `22 / 01 / 00` | 8 байт результата; decrypt(encrypt(data)) = data |
| CBC и обратное преобразование | После установки IV: те же команды с P2 = `01` | Round-trip с одинаковым IV |
| 16-байтовый ключ | `20 / 01 / 00`, 16 байт; затем `22`, 8 байт | NullPointerException в getDesKey |

Исходник трактует любой ненулевой P1 шифрования как decrypt и любой ненулевой P2
как CBC; строгую проверку этих значений он не выполняет.

## Источники формата

Для бинарных полей и инструкций сверены разделы 6.4, 6.5, 6.9, 7.5.16 и 7.5.54
[Oracle Java Card VM Specification 3.0.5](https://docs.oracle.com/cd/E59935_01/JCVMS.pdf).
Это проверка формата CAP 2.2 и инструкций, а не заявление о версии присланного SDK.
